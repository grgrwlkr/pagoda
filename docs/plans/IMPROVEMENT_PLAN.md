# План улучшений проекта

На основе анализа текущего состояния проекта и рекомендаций из README.md, составлен следующий план улучшений.

## Критичные проблемы

### 1. Использование `ctx.FormValue()` вместо форм с валидацией

**Проблема:** В `handlers/messenger.go` используется прямое чтение формы через `ctx.FormValue()` вместо системы форм с валидацией, описанной в README.md.

**Места:**
- `WorkspaceCreate()` (строки 545-558)
- `WorkspaceUpdate()` (строки 677-707)
- `ChannelCreate()` (строки 1169-1180)
- `ChannelUpdate()` (строки 1412+)
- И другие места

**Решение:**
- Использовать формы из `pkg/ui/forms/messenger/` (уже существуют `WorkspaceForm`, `ChannelForm`)
- Использовать `form.Submit()` для обработки форм с автоматической валидацией
- Следовать паттерну из `handlers/auth.go` (строки 79, 257, 352)

**Пример правильного использования:**
```go
func (h *Messenger) WorkspaceCreate(ctx echo.Context) error {
    var input forms.WorkspaceForm
    
    err := form.Submit(ctx, &input)
    switch err.(type) {
    case nil:
        // Продолжаем обработку
    case validator.ValidationErrors:
        return h.WorkspaceCreatePage(ctx) // Перерендер с ошибками
    default:
        return err
    }
    
    // Используем input.Name, input.Slug, input.Description
    // ...
}
```

### 2. Прямое чтение HTMX заголовков вместо `htmx.GetRequest()`

**Проблема:** В `handlers/messenger.go` используется `ctx.Request().Header.Get("HX-Request")` вместо `htmx.GetRequest(ctx)`.

**Места:**
- Строки 608, 1229, 1896, 2104, 2456, 3016

**Решение:**
- Использовать `htmx.GetRequest(ctx).Enabled` вместо прямого чтения заголовка
- Использовать `htmx.Response{Redirect: url}.Apply(ctx)` вместо прямого `ctx.Response().Header().Set("HX-Redirect", ...)`

**Пример:**
```go
// Было:
if ctx.Request().Header.Get("HX-Request") != "" {
    ctx.Response().Header().Set("HX-Redirect", redirectURL)
    return ctx.NoContent(http.StatusOK)
}

// Должно быть:
if htmx.GetRequest(ctx).Enabled {
    htmx.Response{Redirect: redirectURL}.Apply(ctx)
    return ctx.NoContent(http.StatusOK)
}
```

### 3. Защита от паники в `r.Path()` - плохая практика

**Проблема:** В `pkg/ui/components/messenger/channel_list.go` (строки 34-43) используется `defer recover()` для защиты от паники при вызове `r.Path()`. Это маскирует реальную проблему.

**Решение:**
- Исправить `r.Path()` в `pkg/ui/request.go` чтобы он не паниковал
- Убрать все `defer recover()` из компонентов
- Убрать fallback пути из `channel_list.go` (строки 28-47)

**Текущее состояние `request.go`:**
- Уже есть защита от паники в `r.Path()` (строки 112-121)
- Есть fallback функция (строки 161-213)
- Но проблема в том, что компоненты все равно используют дополнительную защиту

**Решение:**
- Убедиться, что `r.Path()` всегда возвращает валидный путь (не пустую строку)
- Убрать все дополнительные проверки из компонентов

## Важные улучшения

### 4. Избыточное логирование

**Проблема:** В `handlers/messenger.go` используется избыточное логирование с маркерами `=== START ===` и `=== END ===`.

**Примеры:**
- Строки 403-404, 428, 432, 440, 448, 500, 539, 612, 616, и многие другие

**Решение:**
- Убрать маркеры `=== START/END ===`
- Оставить только важные логи с контекстом
- Использовать структурированное логирование (уже используется через `log.Ctx(ctx)`)

**Рекомендация:**
- Логировать только важные события: начало операций, ошибки, успешные завершения
- Не логировать каждый шаг внутри функции

### 5. Использование прямых путей вместо `r.Path()`

**Проблема:** В некоторых местах используются прямые пути вместо генерации через `r.Path()` с route names.

**Места:**
- `channel_list.go` строка 31: `fmt.Sprintf("/workspace/%d/channels/create/form", workspaceID)`
- `workspace.go` строка 43: `r.Path("messenger.channel.create.form", workspaceID)` - правильно, но есть проблемы

**Решение:**
- Использовать `r.Path()` везде, где это возможно
- Убедиться, что все route names определены в `pkg/routenames/names.go`
- Исправить `r.Path()` чтобы он работал надежно

### 6. Использование `ctx.Redirect()` вместо `redirect.New()`

**Проблема:** В некоторых местах используется прямой `ctx.Redirect()` вместо пакета `redirect`, который поддерживает HTMX.

**Места:**
- `messenger.go` строка 352: `return ctx.Redirect(http.StatusFound, "/user/login")`

**Решение:**
- Использовать `redirect.New(ctx).Route(...).Go()` для всех редиректов
- Это обеспечит правильную работу с HTMX boosted requests

**Пример:**
```go
// Было:
return ctx.Redirect(http.StatusFound, "/user/login")

// Должно быть:
return redirect.New(ctx).
    Route(routenames.Login).
    Go()
```

### 7. Обработка ошибок

**Проблема:** Не везде используется helper `fail()` для обработки ошибок.

**Решение:**
- Использовать `fail(err, "описание")` для всех внутренних ошибок
- Использовать `echo.NewHTTPError()` только для ошибок валидации/авторизации
- Следовать паттерну из `handlers.go` (строки 32-36)

### 8. Валидация форм

**Проблема:** Не все операции создания/обновления используют формы с валидацией.

**Текущее состояние:**
- Формы определены в `pkg/ui/forms/messenger/`:
  - `workspace.go` - WorkspaceForm
  - `channel.go` - ChannelForm
  - `message.go` - MessageForm
- Но не все handlers используют эти формы

**Решение:**
- Использовать формы для всех операций создания/обновления
- Добавить валидацию в формы (уже есть через struct tags)
- Использовать `form.Submit()` для обработки
